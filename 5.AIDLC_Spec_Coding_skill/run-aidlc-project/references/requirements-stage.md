## 目录

1. 输入检查

3. 提问规则

5. 编号与追踪
6. 完成门禁

## 1. 输入检查

先读取用户初始描述、已有项目文档和 `.aidlc/plan/req-plan.md`。若需求目录已有文件，也要完整读取并判断是继续、补充还是修订，禁止无理由重写。

评估以下方面是否清楚：

- 目标用户、角色、权限边界
- 核心业务对象及生命周期
- 正常流程、异常流程和批量操作
- 数据输入、输出、导入导出和保留要求
- 外部系统、认证方式、通知与失败处理
- AI 能力边界、人工确认、降级和可追溯要求
- 部署环境、技术限制、规模、性能、安全和合规
- MVP 范围、明确不做事项和可验证验收标准

## 2. 需求计划

使用以下结构创建或续写 `.aidlc/plan/req-plan.md`：

```markdown
# 需求分析计划

## 上下文
- 初始需求：
- 当前状态：
- 最近更新：

## 执行计划
- [ ] 分析现有输入和缺口
- [ ] 完成关键问题确认
- [ ] 编写功能需求
- [ ] 编写非功能需求
- [ ] 编写用户故事与场景
- [ ] 汇总需求清单并检查一致性

## 问答记录
### Q-001
[Question]
问题正文

[Answer]

## 决策与变更
- 日期：决定、来源、影响
```

保留历史问答。用户在聊天中回答时，把答案准确写回 `[Answer]`，再继续执行。

## 3. 提问规则

- 只问会显著影响范围、验收、架构或安全的缺失信息。
- 合并相关问题，优先一次提出 3 至 7 个关键问题。
- 不询问可从仓库、已有文档或用户答案直接得到的信息。
- 不替用户决定业务规则。可以列出选项及影响，但保持 `[Answer]` 空白。
- 如果用户明确授权采用合理默认值，记录授权和默认值来源后继续。

## 4. 需求产物

至少生成：

- `.aidlc/requirements/functional-requirements.md`
- `.aidlc/requirements/non-functional-requirements.md`
- `.aidlc/requirements/user-stories.md`
- `.aidlc/requirements/requirements-checklist.md`

`functional-requirements.md` 应包含范围、角色、领域模块、业务规则、状态流转、权限、数据、集成、AI 能力、异常处理和验收标准。

`non-functional-requirements.md` 应包含本地/目标部署、性能容量、可用性、可靠性、安全隐私、审计、可维护性、可观测性、兼容性、备份恢复和 AI 特有约束。无法量化的指标标记为待确认，不伪造数值。

`user-stories.md` 为每个关键角色给出用户故事和主要使用场景。场景至少描述前置条件、主流程、异常/替代流程和预期结果。

`requirements-checklist.md` 汇总所有需求，包含编号、简述、优先级、来源、验收依据、状态和关联用户故事，作为设计阶段的追踪入口。

## 5. 编号与追踪

使用稳定编号：

- `FR-xxx`：功能需求
- `NFR-xxx`：非功能需求
- `US-xxx`：用户故事
- `SC-xxx`：使用场景
- `CON-xxx`：约束

修订时保留已有编号。废弃项标记为“已废弃”并记录原因，不把编号重新分配给其他需求。

每条功能需求应具备：

```markdown
### FR-001 标题
- 描述：
- 参与角色：
- 前置条件：
- 业务规则：
- 正常结果：
- 异常处理：
- 验收标准：
- 优先级：
- 来源：
```

## 6. 完成门禁

- 计划复选框全部完成，无空白 `[Answer]`。
- 四类需求产物均存在且互相一致。
- 每项核心需求有可验证验收标准，不使用“友好”“快速”“智能”等不可检验表述代替标准。
- 角色权限、状态转换、工作量/进度口径、外部集成失败、AI 人工确认与降级均有明确规则或待确认项。
- 需求清单覆盖全部 `FR`、`NFR`、`US`、`SC` 和约束，没有孤立编号。
