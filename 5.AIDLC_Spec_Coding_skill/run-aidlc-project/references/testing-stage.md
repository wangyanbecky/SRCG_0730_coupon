# 测试与缺陷修复阶段

## 1. 建立或恢复计划

先完整读取需求、任务、设计中的验证约束和现有测试。使用以下结构创建或续写 `.aidlc/plan/test-plan.md`：

```markdown
# 测试计划与报告

## 测试环境
- 日期：
- 版本/提交：
- 操作系统与运行时：
- 服务与依赖：
- 测试数据：

## 测试用例
### TC-001 场景名称
- [ ] 状态：未执行
- 需求引用：FR-001, NFR-003
- 前置条件：
- 操作步骤：
- 预期结果：
- 实际结果：
- 证据：
- 缺陷：

## 缺陷记录
### BUG-001 标题
- 严重级别：
- 关联用例：
- 复现：
- 根因：
- 修复：
- 验证：

## 回归测试
- [ ] RT-001：

## 测试结论
- 通过：
- 失败：
- 未执行及原因：
- 残余风险：
```

已有计划时，从最后未完成测试继续，不重跑全部已通过项目，除非代码变化使结果失效。

## 2. 覆盖策略

优先覆盖：

- 核心角色的端到端主流程
- 权限拒绝和跨项目/团队数据隔离
- 核心对象状态流转、工作量和进度计算
- 批量操作、依赖、里程碑和健康度
- 外部通知、命令回调、重试和失败降级
- AI/Agent 工具权限、人工确认、结构化输出和非 AI 降级
- 导出数据正确性
- 关键兼容性、性能、安全和可恢复要求

避免为低价值组合穷举；测试深度与风险和变更范围匹配。

## 3. 真实执行

- 启动应用及实际依赖或项目认可的本地替身，记录启动日志和版本。
- 执行自动化测试、API 调用、数据库检查和必要 UI 操作。
- 用响应、日志、持久化结果、截图或测试报告作为证据。
- “代码看起来正确”不是通过证据。因凭证、网络或平台环境无法执行时标记“阻塞/未执行”，说明缺口，不勾选。
- 测试通过后立即填写实际结果和证据并勾选，保持计划可随时恢复。

## 4. 缺陷修复

失败后先稳定复现并定位根因，判断问题属于需求、设计、实现、配置还是测试。修复应恢复正确的不变量，避免只针对单一输入打补丁。

修复后：

1. 重跑原失败用例。
2. 补充能防止复发的自动化测试。
3. 检查同类路径是否受影响。
4. 更新缺陷记录、任务或设计文档中的失配。
5. 保持相关测试项未勾选，直到证据确认通过。

## 5. 回归与完成门禁

只要修改过代码，就在“回归测试”追加受影响模块、相邻接口和核心主流程测试。全部回归通过后才给出最终结论。

完成条件：

- 所有计划测试已通过，或明确记录并经用户接受的未执行项。
- 所有阻断/严重缺陷已修复并回归；其他残余风险有影响和处置建议。
- 测试结论能对应需求编号，包含真实环境和证据。
- 应用可按项目说明启动并完成核心用户流程。
