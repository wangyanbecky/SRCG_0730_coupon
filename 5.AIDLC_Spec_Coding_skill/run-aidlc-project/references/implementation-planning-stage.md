# 实现计划阶段

## 1. 输入

按以下顺序完整读取：

1. `.aidlc/requirements/` 全部文件
2. `.aidlc/design/` 全部文件
3. 已有 `.aidlc/tasks.md`
4. 项目清单、构建配置和现有 `src/` 概况

使用 `nl -ba <文件>` 获取稳定的当前行号。引用格式为 `相对路径:行号`，引用内容修订后同步更新行号。

## 2. 任务组织

- 按基础设施与工程骨架、领域模型、后端能力、集成、前端流程、AI/Agent、端到端验证的实际依赖排序。
- 每项任务产生独立可观察价值，通常可在一个连续工作段完成。
- 不把每个文件或函数拆成任务，也不把整个领域压成无法验收的大任务。
- 明确 `Depends on`；禁止隐含循环依赖。
- 任务必须覆盖需求和设计追踪矩阵中的全部范围。

## 3. `.aidlc/tasks.md` 格式

```markdown
# 实现任务

## 审阅状态
- 状态：待审阅
- 最近审阅：
- 范围基线：

## 任务

### T-001 标题
- [ ] 状态：未完成
- 目标：
- 范围：
- 不包含：
- Depends on：无
- 需求引用：`.aidlc/requirements/functional-requirements.md:42`
- 设计引用：`.aidlc/design/api-specification.md:88`
- [Reference] 外部 API 文档：
- 实现要点：
- 验收标准：
  - 可观察、可测试的结果
- 验证方式：
  - 具体测试或运行命令
- 交付物：
```

复选框默认不勾选。外部库只有在仓库、本地文档或可用官方资料中无法可靠确定其契约时，才保留空白 `[Reference]` 并提醒用户提供；常见成熟依赖无需机械添加。

## 4. 审阅门禁

生成任务后将状态保持为“待审阅”，向用户总结任务数量、主依赖链和需要补充的引用。用户明确认可或明确要求直接开始实现后，记录：

```markdown
## 审阅状态
- 状态：已认可
- 最近审阅：YYYY-MM-DD，用户明确要求继续实现
- 范围基线：需求与设计文档更新时间
```

未认可前可以按反馈修订任务，但不进入批量开发。

## 5. 完成检查

- 所有任务有唯一编号、复选框、目标、范围、依赖、引用、验收和验证方式。
- 引用精确到当前行号且路径可在命令行访问。
- 每项需求至少被一个任务覆盖，每个任务能追溯到需求或必要工程约束。
- 任务顺序可执行，前置能力先于依赖它的功能。
- 测试、迁移、配置、文档和集成失败处理未被遗漏。
