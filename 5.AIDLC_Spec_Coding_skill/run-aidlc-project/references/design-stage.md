## 2. 设计原则

- 按业务能力划分高内聚领域，明确领域所有权和跨领域接口。
- 选择满足已知规模和部署约束的最直接架构，避免未经需求支持的微服务或平台化设计。
- 描述“做什么”和“如何组织”，不写控制器、组件或数据库访问的具体实现代码。
- 可使用 Mermaid 图、表结构、JSON 示例、状态机和时序图表达契约。
- 对鉴权、幂等、并发、事务边界、错误码、审计、重试和降级作明确设计。
- AI/Agent 设计必须包含工具边界、权限继承、人工确认、记忆/上下文、可观测性、超时重试和非 AI 降级路径。

## 3. 必需产物

至少生成：

- `.aidlc/design/system-architecture.md`
- `.aidlc/design/database-design.md`
- `.aidlc/design/api-specification.md`

- `.aidlc/design/traceability-matrix.md`

### 系统架构

记录上下文、领域划分、组件职责、依赖方向、关键流程、部署拓扑、安全边界、外部集成、故障与降级策略。

### 数据库设计

记录实体、字段、类型、约束、索引、关系、生命周期、审计字段、软删除/归档、事务一致性及迁移策略。对进度、工作量、依赖和风险指标给出统一计算口径。

### API 规范

为每个接口记录方法、路径、权限、请求、响应、错误、幂等和分页/筛选规则。事件或 Webhook 记录事件结构、签名校验、重放防护、重试和死信策略。

### 前端设计

记录路由、信息架构、页面与组件职责、状态管理、权限可见性、加载/空/错误状态、列表与看板交互、批量操作和响应式策略。

### 技术栈

记录语言、框架、版本策略、数据库、测试、构建、部署、AI/Agent SDK 和外部服务。每项说明选择理由、约束和替代方案，不虚构未确认版本。

## 4. 决策与提问

先从需求和仓库惯例推导设计。仅当某项决定会造成显著成本、安全或不可逆影响且无法合理推导时，写入 `[Question]` 并等待回答。典型问题包括部署边界、身份源、数据库类别、外部平台凭证模式和模型提供方。

不把普通实现细节升级为用户问题。低风险选择由架构师按现有项目模式决定，并记录理由。

## 5. 追踪和完成门禁

`traceability-matrix.md` 至少包含：需求编号、设计章节、数据实体/API/页面、计划验证方式、未解决事项。

完成条件：

- 设计计划全部勾选，无空白 `[Answer]`。
- 每项 `FR` 和关键 `NFR` 都有设计归属，无孤立需求。
- 领域职责和接口无明显重叠或循环依赖。
- 数据模型、API 和前端使用同一术语、状态和权限定义。
- 外部集成、Agent、风险计算和失败降级具有可实现契约。
- 文档没有具体业务代码，且足以支持后续任务拆分。
