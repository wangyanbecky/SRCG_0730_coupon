# 非功能需求

### NFR-001 兼容性
- 保持 Flask、SQLAlchemy、Jinja 和原生 CSS 技术栈，不新增依赖或数据库迁移。
- 保持现有 operator 页面路由和活动操作链接兼容。

### NFR-002 安全与可靠性
- 查询参数仅参与 ORM 过滤和白名单排序，不拼接原始 SQL。
- 未知或缺失的排序参数必须安全回退。

### NFR-003 可用性
- 搜索栏位于列表首行（表头）上方。
- 控件应包含可识别标签，支持键盘提交，并适配现有移动端布局。
- 无结果状态应说明当前搜索关键字并提供清除入口。

### NFR-004 可维护性
- 查询、筛选和排序集中在 operator dashboard 路由。
- 模板只负责控件和结果渲染；样式复用项目现有变量和组件风格。

### NFR-005 数据完整性与幂等
- 用户与活动预约使用数据库唯一约束，重复预约不得产生重复记录。
- 预约操作不得改变优惠券库存、用户积分或已领取数量。
- 旧数据库通过现有 `db.create_all()` 启动流程补建新表，不破坏既有表和数据。

### NFR-006 状态一致性与安全
- operator 展示状态、用户待发布标识和服务端时间校验使用同一待发布判定语义。
- 预约和领券端点继续受普通用户身份校验保护，活动 ID 必须在服务端验证。
- 时间以服务端 `datetime.now()` 为准，不信任浏览器时间。

### NFR-007 日志安全与隐私
- 日志不采集请求体、Cookie、Authorization、完整查询串或环境变量。
- 写入和读取时对 password、secret、token、key、session、phone、Bearer、数据库 URI 和云凭据模式进行脱敏。
- 日志页面仅 admin 可访问；普通用户、operator 和 verifier 不得查看。

### NFR-008 容量与可靠性
- 使用标准库 `RotatingFileHandler`，默认单文件 5 MiB、保留 5 份备份，参数可由环境变量调整。
- 日志读取默认 50、最大 100，仅扫描当前日志最新 2000 行；损坏行隔离。
- 日志写入或单项健康检查失败不得导致业务请求失败。

### NFR-009 可验证且诚实的可观测性
- 健康页只把实际执行的检查标记为健康；未主动探测的 AI 必须标明配置状态。
- 数据库和日志检查记录毫秒级耗时或明确不可用原因。
- 报警占位不得伪造一期不存在的监控、通知或处置能力。
